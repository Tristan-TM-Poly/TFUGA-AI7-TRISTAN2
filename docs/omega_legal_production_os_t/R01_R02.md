# Ω-LEGAL-PRODUCTION-OS-T∞ — R0.1/R0.2

## Scope

This foundation creates a common control model for:

- external email;
- releases;
- payments;
- signatures;
- government filings;
- incorporation;
- production activation.

R0.1 implements the immutable action envelope, authority model, approvals,
default-deny OAK gate, state machine, evidence ledger and anti-replay
reservation. R0.2 implements deterministic release-candidate preparation and
unsigned provenance statements.

No external connector is enabled by this release.

## Control-plane separation

```text
GitHub
  policies, code, schemas, hashes, tests, requests and redacted evidence

External vault
  credentials, private keys, government identities and provider secrets

Provider
  actual email, release, payment, signature, filing or deployment operation

Evidence ledger
  reservation, provider acceptance, effect confirmation and reconciliation
```

GitHub must never contain passwords, API keys, private keys, full banking
coordinates, identity documents, tax credentials or government login data.
The Python models reject common secret-like payload keys before an action can
be created.

## Universal action chain

```text
DRAFT
→ NORMALIZED
→ VALIDATED
→ RISK_SCORED
→ AUTHORITY_RESOLVED
→ READY_FOR_APPROVAL
→ APPROVED
→ RESERVED
→ EXECUTION_STARTED
→ PROVIDER_ACCEPTED
→ EFFECT_CONFIRMED
→ RECONCILED
→ CLOSED
```

Failure and review states include:

```text
REQUIRE_INFORMATION
REQUIRE_SECOND_APPROVAL
REQUIRE_PROFESSIONAL_REVIEW
EXPIRED
REVOKED
PROVIDER_REJECTED
EFFECT_UNKNOWN
RECONCILIATION_FAILED
QUARANTINED
BLOCKED
ROLLED_BACK
```

Provider acceptance is deliberately distinct from the real-world effect.

## Action hash

The canonical action hash covers:

- action and company identifiers;
- action type;
- requester and timestamp;
- purpose;
- canonical payload;
- risk and approval requirements;
- policy;
- source issue and commit;
- evidence references and metadata.

It excludes the mutable workflow state and approval list. Therefore an
approval remains bound to the exact request while state progression and the
append-only approval history remain representable.

## Authority

An `AuthorityGrant` is bounded by:

- person;
- company;
- role;
- permission;
- optional amount limit;
- optional jurisdictions;
- validity interval;
- revocation state;
- evidence hash.

The gate compares each approval with a matching authority grant. Two-person
actions require two distinct approvers; duplicate names are rejected.

## Professional review

Signature, government filing and incorporation actions require evidence whose
identifier begins with:

```text
professional-review:
```

This identifier is only a reference to reviewed evidence. It is not a legal
opinion and must not contain confidential content.

## Ledger

The `ActionLedger` stores JSONL entries containing only:

- sequence;
- UTC timestamp;
- action identifier and hash;
- action type;
- hashed company identifier;
- bounded event;
- provider name;
- hash of the provider result;
- previous-entry and current-entry hashes.

It does not store the payload, amount, recipient, document, credentials or
provider response. A `RESERVED` entry is written before any future external
attempt. A second reservation for the same action hash is blocked.

A stale `.lock` file requires manual investigation. It is not safe to delete
it automatically without determining whether a provider operation may have
started.

## Release R0.2

A release candidate requires:

- exact `owner/repository`;
- full 40-character commit SHA;
- semantic version and matching `v<version>` tag;
- at least one uniquely named artifact;
- SHA-256 and size for every artifact;
- content-addressed changelog and SBOM;
- passing tests, license, SBOM and installation gates;
- security gate marked `PASS` or `NOT_APPLICABLE`.

The dry-run provider creates:

- release hash;
- planned tag;
- artifact count;
- hash of an unsigned SLSA-inspired attestation statement.

It does not create a tag, GitHub release, package publication or deployment.

## CLI

Create a template:

```bash
omega-legal-production init-action --out action.json
```

Validate and hash:

```bash
omega-legal-production validate action.json
omega-legal-production hash-action action.json
```

Create one hash-bound approval:

```bash
omega-legal-production approve action.json \
  --approver tristan \
  --role director \
  --out approval.json
```

Evaluate preparation or execution readiness:

```bash
omega-legal-production gate action.json
omega-legal-production gate action-with-approvals.json \
  --grants grants.json \
  --execute
```

Audit a private ledger:

```bash
omega-legal-production audit-ledger /private/actions.jsonl
```

Prepare a release without external effects:

```bash
omega-legal-production release-dry-run release.json \
  --workflow-ref .github/workflows/release.yml@refs/heads/main \
  --receipt receipt.json
```

Generate and audit the versioned policy taxonomy:

```bash
omega-legal-atlas generate generated/legal-production-atlas
omega-legal-atlas audit generated/legal-production-atlas
```

The current taxonomy contains:

```text
7 action types
× 8 risk modes
× 7 autonomy levels
× 3 layers
= 1,176 cells
```

This is a classification taxonomy, not a fixed operational throughput cap.

## CI boundaries

CI uses `contents: read` and performs only:

- compilation;
- targeted tests;
- CLI import checks;
- deterministic atlas generation and audit;
- artifact upload.

CI receives no production credentials and cannot execute an external action.
