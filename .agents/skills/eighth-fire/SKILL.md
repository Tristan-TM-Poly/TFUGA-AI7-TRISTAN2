# Eighth Fire — Capability OS constitutional skill

Use this skill after intent and beneficiaries are explicit, before describing a transformation as an Eighth-Fire success.

## Canonical routing

Do not create a separate Eighth-Fire runtime when Capability OS can express the transformation.

`Intent -> Capability OS -> Virtual Tristan/minimum swarm when needed -> Eighth-Fire beneficiary court -> constitutional gates -> prospective transfer evidence -> OAK/authority -> HOLD|PASS`

## Required distinctions

- `Generated != Verified`
- `GatePASS != MoralTruth`
- `EvidenceOfBenefit != AuthorityToAct`
- `SystemPerformedTask != BeneficiaryAcquiredCapability`
- `CapabilityLeftBehind != VerifiedLongTermEmpowerment`
- `DiagnosticScore != MoralScore`
- `ExpectedBeneficiarySet != CompleteBeneficiarySet`
- `IdentitySeparation != StatisticalIndependence`
- `PASS-Québec != ValidationElsewhere`

## Non-compensatory constitutional gates

Require explicit supplied evidence for:

1. evidence
2. safety
3. non-domination
4. attribution/consent
5. regeneration
6. beneficiary autonomy
7. rollback/contestability

A failure cannot be compensated by a high aggregate score.

## Beneficiary-flow procedure

1. Name expected beneficiaries explicitly.
2. State the capability intended to remain after support is removed.
3. Record autonomy, forkability, reciprocity, dependency, capture, harm and dependency half-life.
4. Run the beneficiary n+1 check for omitted declared beneficiaries.
5. Run constitutional gates.
6. Prefer the minimum sufficient Virtual Tristan population or simpler baseline.
7. Run prospective proof-of-transfer when real beneficiary capability is claimed.
8. Keep execution authority in Capability OS / real governance; 8F never grants authority itself.

## Prospective proof-of-transfer

Freeze criteria before observing the intervention outcome:

`baseline -> assisted task -> system withdrawal -> independent task -> delayed replay -> dependency check -> frozen evaluator -> receipt`

A transfer claim must HOLD when:

- criteria digest changes after freeze;
- generator and evaluator collapse into one actor when separation is required;
- the system remains available during the claimed withdrawal test;
- post-withdrawal dependency exceeds the frozen threshold;
- withdrawal or delayed retention falls below the frozen threshold;
- delayed capability does not beat baseline when required.

## Mandatory n+1 attacks

- omitted beneficiary
- hidden persistent dependency
- simpler comparable intervention
- metric Goodhart attack
- externalized harm/cost
- practical revocation/exit failure
- vanishing-system test
- lower-capture decentralized alternative
- evaluator/source collusion
- cultural-authority overclaim

## Cultural boundary

This repository's Eighth-Fire architecture is Tristan's personal normative/engineering construction. Never represent it as authoritative Indigenous doctrine, as speaking for Anishinaabe peoples, or as proving a cultural interpretation.

## Québec-first boundary

Québec is the first intended real-world validation anchor. A local PASS can at most make controlled further testing eligible; it does not establish transfer to other populations or jurisdictions.

## Anti-inflation

Before adding a new Eighth-Fire class, agent, runtime or ontology, test whether the need can be represented as an existing Capability OS `Role`, `Probe`, `Gate`, `Receipt`, `Metric` or `Profile`.

`SEARCH -> REUSE -> COMPOSE -> EXTEND -> CREATE`

If ablation of a new abstraction changes no verified capability, evidence, authority boundary or falsifiable behavior, PRUNE it.
