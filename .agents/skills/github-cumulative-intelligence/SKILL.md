# GitHub Cumulative Intelligence

Use this skill before proposing or drafting a new PR in this stack.

1. Refresh canonical `GitHubMemoryIndex` snapshots with the existing #447 `state=all` snapshotter.
2. Include every relevant repository index. Do not discard merged or closed-not-merged PRs.
3. Compile `omega_capability_os_t.github_cumulative_intelligence_cli`.
4. Read the minimal reuse coalition, relevant PR genomes, lineage neighborhood and negative-memory hits.
5. Run the leakage-controlled `github_retrieval_arena` policy when historical ancestry/reuse candidates matter. The current `hybrid_rrf` policy is **probationary**, not canonical truth. Its frozen v0.1 ranker improved Recall@8 on the #450 v0.2 retrospective baseline and then reproduced that gain without retuning on two additional repositories in the same Tristan ecosystem. Cross-repository retrospective replication is stronger evidence, but it is still not prospective or independent external validation.
6. Treat retrieval rankings as an inspection queue only. Progressively inspect exact candidate heads/files/tests before reusing implementation; a high rank never proves semantic equivalence or implementation compatibility.
7. Reuse/compose/extend before creating. Create only declared residual outputs.
8. Keep provenance to repository, PR and exact head SHA.
9. Treat `MERGED != M+`, `CLOSED != M-`, similarity != semantic equivalence, AST symbols != reusable behavior, stack-parent metadata != semantic dependency proof, cross-repo replication != prospective validation, and arena winner != generalization.
10. Keep LLMT views on one canonical memory substrate; multiple views/models are not independent evidence.
11. Never infer GitHub write authority from generation scope. Writes, merges, publication and irreversible actions remain separately authorized.
12. After evidence exists, emit a `ReuseOutcomeReceipt` so useful failures/successes feed M-/M+/M? instead of being forgotten.
13. Preserve the frozen retrospective baseline under `benchmarks/omega_pr_retrieval_arena_v02_baseline.json` and the cross-repository receipts under `benchmarks/omega_pr_retrieval_cross_repo_replication_v01.json`.
14. Do not tune ranking weights on those retrospective cases. Accumulate future eligible PRs as untouched prospective cases before promotion.
15. Before promoting the ranker from probationary status, require zero temporal leakage, stable prospective Recall@k/MRR, exact-source transplant tests, measured engineering outcomes, and replication outside the same project ecosystem when a comparable corpus is available.
